# db/ — Claude notes

Loaded only when working under `db/`. Project-wide invariants (cents, ids, state sets) are summarized in the root `CLAUDE.md`.

## Database
SQLite is accessed from Go via `jmoiron/sqlx`. All schema migrations live in `db/migrations/` as `*.up.sql` files and run automatically on every startup. The database file is located at:
- **Docker**: `/data/sqlite.db` (mount a volume at `/data`)
- **Local dev (macOS)**: `~/Library/Application Support/FaturaCloud/sqlite.db`
- **Local dev (Linux)**: `~/.config/FaturaCloud/sqlite.db`

Schema conventions:
- Primary keys are 21-character nanoid strings — every `Create*` path guards a client-supplied empty `req.ID` with `if req.ID == "" { req.ID, _ = gonanoid.New() }` (`CreateInvoice` was once missing this guard, letting `{"id": ""}` insert an empty-string primary key; a later sweep found `CreateDelivery`, `CreateOrder`, `CreateOrganization`, and `CreateTaxRate` were missing it too — all four now have it)
- Monetary values stored as integer cents — the form layer converts (user input × 100 → store; stored ÷ 100 → display); atoms and API pass cents through unchanged. Every line-item `unitPrice`/`unitCost` insert (`db/invoice.go`, `incoming_invoice.go`, `order.go`, `purchase_order.go`, `inbound_delivery.go`) converts its incoming `float64` cents value via `roundCents` (`db/invoice_totals.go`) — `math.Round`, half away from zero — rather than a plain `int64(x)` cast, which truncates toward zero and could disagree with `validateInvoiceTotals`' decimal-rounded totals by up to a cent for a fractional-cent value arriving through JSON
- Dates stored as Unix timestamps in milliseconds
- Organization logo stored as BLOB (raw bytes), read and written exclusively through `GET/POST/DELETE /api/organizations/{id}/logo` (`db.GetOrganizationLogo`/`SetOrganizationLogo`) rather than as a field on the organization JSON — `db.Organization` has no `Logo` field at all (`json:"-"` alone wouldn't stop `SELECT *` from loading a multi-MB BLOB into memory on every org fetch, so it's dropped from the struct and both `GetOrganizations`/`GetOrganization` use an explicit column list instead). `GetOrganizationLogo` also decodes the legacy storage format from before this endpoint existed, where the column held the browser's full `"data:image/png;base64,..."` string as text rather than raw bytes. On the frontend, `organizationAtom` fetches the logo alongside the organization and converts it to a data URI (`FileReader.readAsDataURL`) so PDF templates and the settings page can keep reading `organization.logo` as a ready image source; the Organizations list edit drawer instead uses a plain `<img src="/api/organizations/{id}/logo">` (cookies travel automatically on a same-origin `<img>` request) since it can be editing an org other than the currently-selected one
- `products.type` is `"product"` | `"service"` (default `"service"`)
- `products.category` (migration `0065`) is `NULL` | `"finished"` | `"component"` — orthogonal to `type`, since "component vs. finished" only ever applies to a physical product (`CreateProduct`/`UpdateProduct` force it to `NULL` whenever `type != "product"`, the same defensive-clear shape `serialized` already gets when `stockEnabled` is off, and reject any value outside `productCategories`). `NULL` means "unclassified" and is the default for every pre-existing row — every product picker treats it as eligible on both sides, so this is opt-in and fully backward compatible: `src/routes/{orders,deliveries,invoices}/details.tsx` filter out `category === "component"` (a component isn't sellable) and `src/routes/{purchase-orders,inbound-deliveries}/details.tsx` filter out `category === "finished"` (a finished good isn't purchasable from a vendor) before passing the list to `LineItemsTable`'s `products` prop — the filter never touches the unfiltered `products` atom itself, since already-saved line items still need it to resolve a product's name/sku by id regardless of what the *picker* currently offers. `src/components/products/form.tsx`'s Category select only renders while `type === "product"`
- `products.unitOfMeasureId` (migration `0076`, `db/unit_of_measure.go`) is the structured Base Unit of Measure — a maintained per-organization list (`units_of_measure`, same "maintained list" shape as `payment_terms`) replacing what used to be a frontend-only suggestion array (`src/utils/units.ts`'s now-removed `UNIT_OPTIONS`). Nullable with `ON DELETE SET NULL`, not `taxRates`' CASCADE-plus-usage-guard pattern — deleting a unit of measure must never delete a product, only clear the link. `products.unit` (the legacy free-text column) stays in the schema and is **server-derived** from `unitOfMeasureId` whenever one is selected (`resolveProductUnit` in `db/product.go`, called from both `CreateProduct`/`UpdateProduct`) — this denormalize-once-at-the-write-boundary shape (the same one BOM version lines use for `componentName`/`Sku`/`Unit`) is deliberate: it keeps every existing reader of `products.unit` (Inventory, Products list, `db/product_bom.go`'s `componentUnit` join) correct with zero changes of its own, rather than needing a join or a frontend fallback rule at every display site. A nil/empty `unitOfMeasureId` leaves `unit` exactly as sent, preserving plain free-text entry for any caller that doesn't use the structured list (`cmd/seed-demo`, a direct API client) — **unless the product currently has one**, in which case the stored `unit` is a derived copy and clearing the link clears the copy too, so a caller that echoes the old text back while nulling `unitOfMeasureId` can't leave a ghost value behind ( before this the guard lived only in the product form, so any other caller reproduced the bug). Because `unit` is a derived copy, **`UpdateUnitOfMeasure` re-derives it for every linked product inside its own transaction when the name changes** — nothing else ever re-derives it, so before this a rename left every linked product displaying the old text indefinitely — `src/components/products/form.tsx`'s "Unit" `Form.Item` was replaced by "Base unit of measure" (a `Select` sourced from `unitsOfMeasureAtom`, writing `unitOfMeasureId`) plus a hidden `unit` field that round-trips the legacy value unedited, since `UpdateProduct` is a full replace, not a partial update — without the hidden field, resaving an old legacy product with no `unitOfMeasureId` selected would silently wipe its `unit` text to null. `SeedDefaultUnitsOfMeasureForAllOrganizations`'s one-time backfill (mirroring `SeedDefaultPaymentTermsForAllOrganizations`'s `COUNT(*)==0`-per-org idempotent gate) links an existing product's `unitOfMeasureId` only on an exact case-insensitive match against the seeded default names — left `NULL` rather than guessed on anything that doesn't match (e.g. `cmd/seed-demo`'s `"pcs"` values don't match the seeded `"piece"` row, by design)
- `products.sku` (labeled "Product code" in the UI) must be unique per organization — enforced by a `UNIQUE(organizationId, sku)` index, not a DB-level `NOT NULL` (SQLite can't add that retroactively without a table rebuild); required-ness is enforced in `api/products.go` and the frontend form instead. The New Product form proposes a code derived from the name, deduplicated against other products in the org
- `stockMovements.quantity` is a **signed delta**: positive = stock in, negative = stock out/adjustment; `products.stockQuantity` is always `SUM(quantity)` over all movements and is recomputed inside a transaction on every insert/delete — never update it directly. Phase 7: a manual movement (`POST /api/stock-movements`, `db.CreateStockMovement`) also posts a GL trace — `buildStockAdjustmentGLLines` builds one signed line against `organizations.defaultInventoryAccountId`/`defaultInventoryAdjustmentAccountId` for the request's *net* value (an uncosted inflow contributes nothing, like GRNI; an uncosted outflow always 409s, like COGS) — and `req.SourceDocumentID` is set to `req.ID` right after generation as a shared batch id for the whole request (previously only the serialized fan-out path used it), which is what lets `FindPostedEntryForSourceDocument("stock_movement", ...)` find and block deletion of a GL-posted movement (`"cannot delete a stock movement with a posted GL entry — record an offsetting adjustment instead"`) regardless of fan-out. No undo/reversal flow for a manual movement, only that delete-block once posted — corrected by recording an offsetting adjustment, consistent with every other posted entry's immutability
- `products.serialized` marks a stock-enabled product as individually unit-tracked rather than fungible-quantity. Only meaningful with `stockEnabled=1` (app-side coerced back to 0 otherwise), and `db.UpdateProduct` blocks toggling it in **either** direction while `stockQuantity` is non-zero (tolerance `1e-9`, since `stockQuantity` is a `SUM(REAL)`) — turning it on would fabricate identity for untracked legacy stock, turning it off would strand the registry with nothing to reconcile against. `product_serial_numbers` is the registry: one row per physical unit, created once and never deleted; a serial's current in-stock status is **computed on read** from the sign of its most recent linked `stockMovements` row (`db.GetProductSerialNumbers`/`lookupSerialNumbersTx`, a windowed query — not stored, same "never goes stale" philosophy as `stockQuantity`/`unitCost`). Serial numbers are unique **per product** (`UNIQUE(organizationId, productId, serialNumber)`), not per org. For a serialized product, every stock movement is posted **one row per unit** (`stockMovements.quantity` always exactly `±1`, carrying `serialNumberId`) instead of one aggregate row per line — `db/stock.go`'s `insertStockMovementRowTx`/`recomputeStockQuantityTx` split exists specifically so this fan-out doesn't pay a `SUM` scan per unit. `stockMovements.sourceDocumentId` (the receiving/shipping document's own row id, deliberately **not** `reference`, which is free text a manual movement could coincidentally reuse) is how a receipt/delivery cancellation finds and reverses exactly the units *it* posted. Manual movements (`POST /api/stock-movements`) restrict a serialized product to `in`/`out` only — `adjustment`/count types have no per-unit mapping — and take a `serialNumbers: string[]` array instead of `quantity`; the response is always `{movements, product}` (possibly many rows) rather than a single movement. Receiving/shipping a serialized line (`PATCH .../status`) requires a `serialNumbers` map keyed by line-item id, validated server-side to exactly match each line's quantity — this is enforced, not optional, so the registry never drifts from what actually moved
- `invoices.state` is validated against the canonical set `"draft"` | `"sent"` | `"paid"` | `"cancelled"` (`invoiceStates` in `db/invoice.go`) on create and on `PATCH /api/invoices/{id}/state`; unknown values are rejected with a 409. Unlike orders/deliveries there's no transition matrix — invoices move freely between states (a bounced payment can send `paid→sent`). State is **not** settable via `PUT` (stripped from `UpdateInvoiceRequest`); the frontend single source of truth is `src/types/invoice.ts` (`INVOICE_STATES`, `invoiceStateColor`, `invoiceStateLabel`)
- `purchase_orders.status` is `"draft"` | `"confirmed"` | `"received"` | `"cancelled"`, enforced by a `CHECK` constraint **and** by `purchaseOrderStatusTransitions` in `db/purchase_order.go` (`PATCH /api/purchase-orders/{id}/status` only — status can't be set through `PUT`). `received` is terminal; `cancelled` (2026-09-09) is **not** — it can fall back to `confirmed`/`received`, safe unconditionally since status changes here have zero side effects (no stock, no GL). Status is never auto-advanced from received quantities; per-line fulfilment is reported separately. **Line items are frozen once a goods receipt against the order has actually been `received`** (`db/purchase_order_freeze.go`) — those lines are the basis of a posted GRNI accrual, of `grniAccrualForPOLine`/`grniClearedQtyForPOLine`'s netting, and of 3-way matching, so moving a quantity or price underneath them silently rewrites what a posted entry was computed from. The freeze is **computed, never stored**, the same philosophy as `products.stockQuantity`: there is no `frozen` column and no unfreeze path, because cancelling the receipt moves it out of `received` and lifts the freeze by construction, and `DeleteInboundDelivery` already refuses to delete a received receipt — so every deletable receipt is one that never froze anything. Only `received` receipts freeze, not merely non-cancelled ones: a draft receipt has moved no stock and posted no GRNI, and is itself freely editable, so freezing for one would block a legitimate edit while protecting no invariant. `purchase_orders.status` is deliberately **not** the signal, precisely because it is never advanced automatically (a user can set it to `received` with no receipt behind it). Both link shapes count — `inbound_deliveries.purchaseOrderId` and a line's own `purchaseOrderLineItemId` — since a standalone receipt carries only the latter and a header-linked receipt's manually added lines carry only the former. Crucially the check rejects a payload that **differs** from what is stored, not one that merely *carries* line items: `src/atoms/purchase-order.ts` always sends the full array, so rejecting on presence would make a received order unsaveable rather than header-only-editable. A consequence worth knowing: this is an all-or-nothing freeze, so a **partially** received order can no longer have its outstanding lines adjusted — cancel the receipt, edit, and re-receive. `UpdatePurchaseOrderStatus` now re-checks the transition inside a transaction (`UPDATE ... WHERE id = ? AND status = ?` plus a `RowsAffected` check) instead of a bare non-transactional `UPDATE` — the same re-check-under-tx guard pattern used everywhere else
- **Line-item ids are stable across an edit for the two documents other tables reference** (`db/line_item_reconcile.go`). Only three FKs in the schema point at a line-item table's `id`: `outbound_delivery_line_items.orderLineItemId` → `orderLineItems(id)`, and both `inbound_delivery_line_items.purchaseOrderLineItemId` and `incoming_invoice_line_items.purchaseOrderLineItemId` → `purchase_order_line_items(id)`. All three are `ON DELETE SET NULL`, so the old delete-every-row-and-reinsert-with-fresh-nanoids save silently and permanently nulled them on every edit — which on the purchasing side made the billed-receipt cancel guard (`db/inbound_delivery.go`, which skips any line whose id is nil) stop running entirely, left GRNI permanently accrued, and made 3-way matching report every line `unlinked`; on the sales side it made the delivery prefill re-offer already-shipped quantity. `CreateOrderLineItemRequest`/`CreatePurchaseOrderLineItemRequest` therefore now carry an **`id`**, which `src/atoms/order.ts`/`src/atoms/purchase-order.ts` echo back on save (they used to `omit` it), and `replaceOrderLineItemsTx`/`replacePurchaseOrderLineItemsTx` reconcile by it: a line the request still carries is `UPDATE`d in place, a line it no longer carries is deleted, a line with no id is inserted fresh. An id that isn't already one of *that* document's own rows is never trusted as a primary key — it falls back to a fresh nanoid, so a client can't point one document's line at another's row. Reconciling by **id, not position**, is deliberate: position matching would keep an id while the row under it became a different product, a stale link that silently points at the wrong line rather than an obviously absent one. The other four line-item tables (invoices, incoming invoices, outbound deliveries, inbound deliveries) have no inbound FK to their own ids at all, so their delete-and-reinsert is harmless and is **deliberately left alone**. A caller that sends no ids (a direct API client) still saves correctly, it just doesn't get the preservation.
- `purchase_orders.vendorId` deliberately has **no `ON DELETE` clause**. Vendor referential integrity is enforced app-side by `DeleteVendor`'s guard; `ON DELETE SET NULL` would silently orphan a purchase order from its vendor and make that guard's rationale false. Any new table with a `vendorId` column must be added to `vendorReferencingTables` in `db/vendor.go` — `TestVendorDocumentCountCoversEveryReference` reads the live schema and fails otherwise
- `purchase_orders.importId` (migration `0066`, F114) follows the identical no-`ON DELETE`-clause precedent for the same reason, one level up: `DeleteImport` (`db/import.go`) guards via `GetImportPurchaseOrderCount`/`ErrImportInUse` rather than a cascade or `SET NULL` that would silently detach a PO (and the landed cost already allocated against it) from its shipment. `imports` itself is transactional data, not master data — listed in `transactionalDataTables` (`db/reset.go`) positioned **after** `purchase_orders` for the same no-cascade-ordering reason `payments` precedes `journal_entries` there
- `inbound_deliveries.status` is `"draft"` | `"received"` | `"cancelled"`, enforced by a `CHECK` constraint and by `inboundDeliveryStatusTransitions` in `db/inbound_delivery.go` (`PATCH` only). Marking a receipt `"received"` inserts `"in"` `stockMovements` (**no availability check** — stock is going up) carrying the line's `unitCost`; cancelling a received receipt inserts reversing `"out"` movements, but **only after validating that every line's quantity is still in stock** — otherwise the goods have already been shipped and reversing would drive `stockQuantity` negative. That guard has no outbound equivalent. Deleting a received receipt is rejected — cancel it instead. Phase 7: receiving also posts a GRNI accrual (`buildReceiptGRNILines`, Dr Inventory / Cr GRNI, skipped rather than posted if every line was uncosted) and cancelling reverses it via `FindPostedEntryForSourceDocument("inbound_delivery", ...)` (a no-op if nothing was ever posted). Cancelling gained a second guard **before** the stock-quantity check — for every line linked to a PO line, `grniClearedQtyForPOLine` must be zero, or the cancel is rejected with "already been billed against this receipt" — otherwise it would reverse the receipt's own GRNI entry while an approved bill's AP obligation and cost recognition still stood, permanently unbalancing GRNI (this was Finding B against the original Phase 7 design note, fixed as part of implementing it). `UpdateInboundDeliveryStatus` re-reads `status` via `tx` immediately after `Beginx()` and aborts if it no longer matches the pre-tx read that the rest of the function's decisions (which lines to move, whether `grniLines`/`existingGRNIEntry` apply) were made against — closing the race where a concurrent request against the same receipt could otherwise double-move stock or reverse a GRNI entry another request already reversed. `cancelled` stays terminal (no un-cancel fallback like purchase orders/orders — see `src/components/status-flow.tsx`), since reversing it would mean re-deriving the stock/GRNI postings above, not just flipping a status column
- `inbound_delivery_line_items.unitCost` is the deliberate divergence from `outbound_delivery_line_items` (which has no price columns): it is what feeds `stockMovements.unitCost` and, through it, the product's average cost. When a line comes from a purchase order and names neither product nor cost, `db.replaceInboundDeliveryLineItemsTx` resolves **both** from the order line
- `products.unitCost` is a **weighted average derived from `stockMovements`**, never adjusted in place — the same philosophy as `stockQuantity` being `SUM(quantity)`. `db.recomputeAverageCostTx` (`db/product_cost.go`) replays the whole history with `math/big` rationals, ordered `createdAt ASC, rowid ASC` (`createdAt` is second-resolution TEXT and ties within a transaction). Costed inflows move the average; uncosted inflows and all outflows move at the running average and leave it unchanged. **Cancelling a receipt does not restore the previous average** — a reversal removes quantity at the *current* average, which is correct weighted-average behaviour. A product with no costed inflow keeps whatever cost the user typed
- `incoming_invoices.state` is `"draft"` | `"approved"` | `"paid"` | `"cancelled"`. Like sales invoices — and unlike orders/receipts — there is **no transition matrix**, only set membership: a bounced payment can send `paid→approved`. State is settable only via `PATCH /state`, which is where 3-way matching is enforced
- **3-way matching** (`db/incoming_invoice_match.go`) compares each invoice line against the purchase order (quantity and unit price) and against goods actually received, counting what *other* `approved`/`paid` invoices already billed for the same order line — that `PreviouslyInvoiced` term is what stops the same goods being billed twice. `PreviouslyInvoiced` used to count any non-cancelled invoice, including drafts, which disagreed with GRNI clearing's own `approved`/`paid`-only definition (`grniClearedQtyForPOLine`, `db/gl_posting.go`) and could flag a spurious variance against a draft bill that might be edited or deleted before ever being approved — a draft has no AP obligation and hasn't touched GRNI. The two are now aligned; the double-billing guard still holds where it matters, since the draft→approved transition re-evaluates the match, so a second bill can't reach `approved` while a first is already there for the same goods. Per-line status is `matched` | `unlinked` | `quantity_variance` | `over_received` | `price_variance`. It is **computed on read, never stored**: a stored flag would go stale as soon as a linked receipt is cancelled. Tolerances come from `organizations.match_price_tolerance_percent` / `match_quantity_tolerance_percent` (both default 0, exposed on Settings → Invoice); comparisons use `math/big` rationals, not float64. This is the matching *report*, separate from GL posting: a stock-enabled bill line's GL entry (`resolvePurchaseAccount`/`resolveGRNIClearing` in `db/gl_posting.go`) capitalizes to Inventory and clears any GRNI the linked receipt already accrued regardless of what this report says about the line — matching can flag a variance without blocking a save, and a variance's *dollar* effect on GRNI clearing is a separate, independent computation from the *quantity/price tolerance* check above
- Matching does **not** block saving — a draft can be saved with variances so they can be investigated. It blocks the move to `approved` (and to `paid` from a non-`approved` state) unless `matchOverride = 1`, and `matchOverrideReason` is **required** when it is: a blank reason would make the override a silent bypass. `unlinked` lines are informational and never block
- `incoming_invoice_line_items` reuses `db.CreateInvoiceLineItemRequest` so incoming invoices go through the same `db.validateInvoiceTotals` as sales invoices rather than duplicating its exact-rational arithmetic; the type gained nil-safe `purchaseOrderLineItemId`/`productId` fields that stay nil on the sales path
- `taxRates` is referenced by **five** tables now (`invoiceLineItems`, `incoming_invoice_line_items`, `purchase_order_line_items` — all with a `taxRate` column — plus `journal_lines.taxRateId` (manual entries) and `products.taxRateId`), listed in `taxRateReferencingTables` in `db/tax_rate.go`. The first two cascade on delete, so a table missing from that list would let an in-use rate be deleted and silently strip line items off existing invoices; the `SET NULL` references (`journal_lines`, `products`) would instead just drop the historical link silently — `TestTaxRateUsageCountCoversEveryReference` reads the live schema and fails if one is missing, matching both `taxRate` and `taxRateId` column names
- `orders.status` is `"draft"` | `"confirmed"` | `"shipped"` | `"delivered"` | `"cancelled"`; transitions enforced both client-side via `orderTransitions`/`orderStatusTransitionMatrix` in `src/types/order.ts` and server-side via `orderStatusTransitions` in `db/order.go` (`PATCH /api/orders/{id}/status` only — status can't be set through `PUT`, which no longer accepts a `status` field). `delivered` is terminal; `cancelled` (2026-09-09) falls back to `confirmed`/`shipped`/`delivered`, the same zero-side-effects reasoning as purchase orders above. `UpdateOrderStatus` gained the same transactional re-check `UpdatePurchaseOrderStatus` did — see that bullet above
- `orderLineItems.unitPrice` stored as integer cents; `orderLineItems.quantity` stored as REAL (supports fractional quantities)
- `outbound_deliveries.status` is `"draft"` | `"shipped"` | `"delivered"` | `"cancelled"`; transitions enforced both client-side in `src/routes/deliveries/details.tsx` and server-side via `deliveryStatusTransitions` in `db/delivery.go` (`PATCH /api/deliveries/{id}/status` only — status can't be set through `PUT`, which no longer accepts a `status` field). Line items are frozen once a delivery is `shipped`/`delivered` — `PUT` still accepts header-field-only edits (tracking number, notes, …). That second half was **false in practice until it was fixed alongside the purchase-order freeze**: the guard rejected on the mere presence of a `LineItems` field and `src/atoms/delivery.ts` always sends the full array, so saving a tracking number on a shipped delivery returned a 409 and the documented header-only edit was unreachable through the very UI whose comment documents it. `db/delivery_freeze.go`'s `deliveryLineItemsUnchangedTx` now compares the payload against what is stored, and only a genuine change is refused. It matches lines **positionally**, not by id, because `outbound_delivery_line_items` has no inbound foreign key to its own ids — `CreateDeliveryLineItemRequest` carries no `ID` field and `replaceDeliveryLineItemsTx` still deliberately deletes and reinserts; an incoming line that names an order line but no product is treated as matching whatever is stored, since `replaceDeliveryLineItemsTx` is what derives that `productId` in the first place. The status it tests is re-read under `tx`, never taken from the pre-tx read (the re-check-under-tx shape). `UpdateDeliveryStatus` re-reads `status` via `tx` immediately after `Beginx()` and aborts if it no longer matches the pre-tx read — the same guard as `UpdateInboundDeliveryStatus` above, closing the race where a concurrent request against the same delivery could double-ship stock/COGS or reverse a COGS entry another request already reversed. `cancelled` stays terminal here too, same reasoning as inbound deliveries above
- `outbound_deliveries.clientId` (migration `0064`) lets a *standalone* delivery (no `orderId`) record who it's for — before this, `ClientID` on the API struct was only ever a value joined from the linked order, so a direct/walk-in shipment had no client attribution at all. `ON DELETE SET NULL` mirrors `orders.clientId`'s own precedent (deleting a client just detaches it, doesn't fail or cascade), so it's exempted from `clientReferencingTables`' app-level guard the same way `orders` already is. `db.OutboundDelivery` distinguishes `OwnClientID` (`db:"clientId"`, the raw column — write side, only ever meaningful when there's no order) from `ClientID` (`db:"effectiveClientId"`, a `COALESCE(order's client, own clientId)` computed in `outboundDeliverySelect` — read side, unchanged in meaning from before this field existed: order's client if there is one, else the delivery's own). The two need distinct `db` tags since both are selected in the same query (`od.*` includes the raw column, plus the computed one) — reusing one tag for both would make sqlx's column-to-field mapping ambiguous. `src/routes/deliveries/details.tsx`'s "Client" picker only renders while no order is linked (`Form.useWatch("orderId")`), and populates from `ownClientId`, never the effective `clientId`, so a stale order-derived value can't leak into the field once an order is cleared
- `outbound_delivery_line_items` has no price columns — delivery notes never show prices
- `outbound_delivery_line_items.productId` links a delivery line to a stock-tracked product — set directly (standalone deliveries) or auto-resolved server-side from `orderLineItemId` when omitted (`db.replaceDeliveryLineItemsTx`, run inside the same transaction as the delivery header write in `CreateDelivery`/`UpdateDelivery`); this is the only field `db.getShippableStockLines` uses to decide which lines affect inventory
- Marking a delivery `"shipped"` (`db.UpdateDeliveryStatus`) validates every stock-enabled product line against `products.stockQuantity` and rejects the transition if any line is short; on success it inserts `"out"` `stockMovements` referenced by `deliveryNumber`. Cancelling an already-`shipped` delivery inserts reversing `"in"` movements. Deleting a `shipped`/`delivered` delivery is rejected — cancel it instead. Phase 7: shipping also posts COGS (`buildDeliveryCOGSGLLines`, Dr COGS / Cr Inventory, resolved via `resolveMovementCost` — the product's average, or a serialized unit's own specific receipt cost) *before* stock is touched, rejecting the whole transition with a 409 if any line has no cost basis at all rather than shipping some lines uncosted; cancelling reverses whatever entry was posted via `FindPostedEntryForSourceDocument("outbound_delivery", ...)`, a no-op if a delivery of only free items never posted one
- `db.GetOrderDeliveredQuantities(orderID)` sums delivered quantity per `orderLineItemId` across non-cancelled deliveries, used to prefill a new delivery from an order with only the outstanding quantity per line (supports full or partial fulfilment)
- `invoiceLineItems.taxRate` has an `ON DELETE CASCADE` foreign key to `taxRates(id)` — deleting a tax rate still referenced by any invoice line item would silently strip those line items off existing invoices. `db.DeleteTaxRate` guards against this via `GetTaxRateUsageCount` and returns `ErrTaxRateInUse` (surfaced as 409) instead of deleting; the frontend only offers deletion for unused tax rates
- `invoices.total`/`taxTotal`/`subTotal` are recomputed and checked server-side against line items + tax rate percentages before every create/update (`db.validateInvoiceTotals` in `db/invoice_totals.go`) and rejected with a 409 on mismatch — the frontend still does the actual computation (`src/routes/invoices/details.tsx` + `src/utils/currency.ts`, decimal.js `ROUND_HALF_UP`), this is a server-side check that it agrees. The Go side uses exact rational arithmetic (`math/big`), not float64, to avoid rounding-boundary mismatches (e.g. a 3.33 unit price at 19.5% tax lands exactly on a half-cent boundary). `UpdateInvoice` validates whenever any of `lineItems`/`total`/`taxTotal`/`subTotal`/`fiscalStampAmount` is present, filling in whichever of those a partial request omits from what's already stored — a request can't bypass the check by sending only new totals (validated against stored line items) or only new line items (validated against stored totals). A pure header-only edit (neither line items nor any total) has nothing financial to recompute and is skipped

The 16 `default*AccountId` columns (the 15 that existed before, plus migration `0079`'s `defaultCashRegisterAccountId` — the physical till, deliberately distinct from `defaultCashAccountId`, which every chart template wires to Bank) were the one exception, by accident rather than decision: `""` is a legal value for a column with no foreign key and an illegal one for a column with, so it failed with a raw constraint violation while `nil` meant "keep" — **neither spelling could unset one**, and the edit drawer's `Select allowClear` offered a clear that did nothing. Those 16 are therefore no longer written through `COALESCE` at all: `UpdateOrganization` emits their SET assignments in Go (omitted → the column isn't in the statement, `""` → `col = NULL`, a value → `col = ?`, with column names from a Go literal and never from the request), which is what lets a foreign-keyed column express the same convention. The migration backfills a membership row for every existing `(organization, user)` pair at that user's then-current global role, and sets `isPlatformAdmin = 1` for every then-`role = 'admin'` user — preserving exactly pre-migration access (every user could already read/write every organization) so nobody is locked out on deploy; only organizations/users created afterward need explicit grants. Migration `0081` then widened `role` from that binary `admin`/`user` CHECK to the six-role set `admin`/`general`/`sales`/`purchasing`/`accounting`/`cashbook` — SQLite can't `ALTER` a `CHECK` in place, so it rebuilds the table and renames every existing `user` row to `general` with identical access. - `db/production_order.go` / `api/production_orders.go` — the actual assembly/production feature `db/product_bom.go`'s recipes and `imports.serialNumberPrefix/RangeStart/RangeEnd` (migration `0073`) were both built to support: `CreateProductionOrder` snapshots a finished product's current BOM (`GetBillOfMaterials`) into the order's own `production_order_component_lines` at creation time (409 if the BOM is empty, or if any component is serialized — see below, or if the finished product doesn't have `stockEnabled = 1`: production orders are a stock-moving path and every other one in this app gates on that column at the SQL level, so without it a stock-disabled "finished" product got real `stockMovements`, a non-zero `stockQuantity` and an Inventory GL entry for a product the rest of the app treats as outside inventory), the same "every document owns its line items" convention every other document type follows, so a later BOM edit never retroactively changes an already-created order. `finishedProductId`/`componentProductId` are nullable with `ON DELETE SET NULL` plus denormalized name **and** `componentSku`/`componentUnit` columns (migration `0077` — `0075` snapshotted only the name and joined the other two from `products` at read time, so they went NULL on a deleted component while the name survived; **serialized components are rejected outright** (creation time and, defensively, again at completion) rather than silently averaged — consuming one as a single aggregate negative movement would leave `product_serial_numbers` reporting a unit "in stock" that was actually just consumed, since the schema invariant for a serialized product is one ±1 movement row per physical unit. The produced finished good is valued at `componentsCostTotal / quantity`, rounded once to the nearest cent (`stockMovements.unitCost` is an integer-cents-per-unit column) — `buildProductionOrderGLLines` (`db/gl_posting.go`) posts the rounding residual, if any, between that per-unit-rounded value and the exact consumed total against `defaultInventoryAdjustmentAccountId`, the same signed-net shape `buildStockAdjustmentGLLines` already uses; in the common case (an exact division — always true for a BOM built from whole-number `quantityPerUnit`s, since order quantity cancels out algebraically) this posts **no GL entry at all**, since Dr Inventory (finished good in) and Cr Inventory (components out) are the same account and net to zero. The organization's Inventory/Inventory Adjustment accounts are nevertheless validated **before** that zero-residual early return, so an unconfigured organization is refused deterministically like every other Phase 7 path rather than succeeding for months and then 409ing on one odd batch. A serialized finished good's produced serials are validated against its linked Import's reserved range when one is configured (`validateSerialAgainstImportRange`) — 409 naming the offending serial and the valid range otherwise; the range itself is a declared pool with no consumption tracker, relying on `product_serial_numbers`' own per-product uniqueness constraint to catch a real re-use. `completed -> cancelled` mirrors `UpdateInboundDeliveryStatus`'s reversal shape exactly: components go back unconditionally (an inflow needs no check), but reversing the produced output needs the same "has it already shipped" guard (`serialInStockByIDTx` for serialized, a stock-quantity comparison otherwise) before any reversal is written. `cancelled` is terminal — no un-cancel, matching inbound/outbound delivery's reasoning (reversing a cancel would mean re-deriving stock/GL/serial state, not just flipping a status column), not purchase orders/orders. No Excel/PDF export and no labor/overhead cost override — explicit, named scope boundaries, not silently missing. - `db/einvoice.go` / `GET /api/invoices/{id}/e-invoice` — renders an invoice as an EN 16931 UBL 2.1 XML document. Country-aware via a small profile registry (`eInvoiceProfile`, `resolveEInvoiceProfile`): only two profiles exist — `"DE"` (XRechnung 3.0, the CustomizationID + mandatory buyer reference) and a generic EN 16931 core profile for every other country (France, UK, US, …), which is a deliberately honest default rather than a guessed CIUS for each of them. The profile is resolved from the **buyer's** country code (`client.CountryCode`, falling back to the seller's `org.CountryCode` only when the buyer's is unset) — e-invoicing mandates like XRechnung are triggered by the recipient's jurisdiction, not the issuer's, which is also why `default_buyer_reference` lives on `clients`. Peppol BIS Billing 3.0 (which would cover GB/US Peppol-network recipients, and is also EN 16931 UBL) is deliberately **not** modeled — it mandates `cbc:EndpointID` with a scheme ID on both parties, which has no column and no reliable scheme to infer; claiming that CustomizationID without it would be a false conformance claim, not a missing-field 409. Beyond the profile, the generator maps only the BT fields with real columns (seller/buyer structured address, VAT ID, tax category + exemption reason, payment terms) and skips the rest of the BR-*/BR-DE-* business rules rather than guessing at them — there is no EN 16931 validator (e.g. KoSIT) available to check against in this environment, so `db/einvoice_test.go`'s golden tests only catch output regressions, not conformance. The Tunisian fiscal stamp is still not emitted (no EN 16931 use case yet). Rejects with a 409 (`*db.ValidationError`) listing every missing mandatory field at once rather than failing on the first. Tunisia's TEIF/TTN e-invoicing (a completely different XML schema requiring a TTN-issued signing certificate) and ZUGFeRD (a PDF/A-3 with this XML embedded, which `@react-pdf/renderer` can't produce) are both explicitly out of scope — separate initiatives, not extensions of this generator
- `db/document_template.go` / `api/document_templates.go` (issue #115) — per-org, per-document-type Excel export template overrides. `document_templates(organizationId, documentType)` (unique index, migration `0068`, `ON DELETE CASCADE` — unlike the `vendorId`/`importId` no-cascade precedent elsewhere, a template override has no independent lifecycle worth guarding) holds the org's uploaded override; `resolveTemplateBytes` falls back to an embedded template (`db/templates_embed.go`, `//go:embed`) when no row exists, picking the layout from the caller-supplied `organizations.documentLayout` (every `Fetch*ExportData` passes `org.DocumentLayout`); `ExportDocumentTemplateBytes` (the template download) reads that column itself and names the file `<type>_<layout>.xlsx`, so a download always matches what an export fills. `IsKnownDocumentType` checks `embeddedDefaultTemplates`' key set and is layout-independent — both maps carry the same six keys. `UploadDocumentTemplate` validates by actually opening the upload with `excelize.OpenReader` before storing it — a stronger bar than the logo upload's `http.DetectContentType` sniff, since this file is later opened and filled by the export engine, not just displayed; a parse failure returns a `*ValidationError` (409). - `db/xlsx_export.go` — the fill engine. `fillTemplate(templateBytes, scalars, blocks, logo, orientation)` is the document-type-agnostic core (marker expansion, placeholder substitution, logo embedding, sheet stripping) every `FillXTemplate` function wraps — it knows nothing about invoices or purchase orders, only a resolved scalar map and a list of repeat blocks, both built by the caller. **As of 2026-09-22 it takes `blocks []repeatBlock` (not a single `lineRows` slice)**, so a template can carry more than one repeatable region: the invoice/VAT-recap layout uses a `{{#lineItems}}` block plus an optional `{{#taxLines}}` block (one row per distinct tax rate; absent marker = block skipped, so the five non-invoice types that don't set it are unaffected). Each block is expanded in turn and its marker re-located every time, because an earlier block's expansion shifts every row below it; the row→placeholder-map association is recorded during expansion so the single substitution pass can look it up by row number. It also takes an optional `logo []byte`: a cell holding exactly `{{organization.logo}}` is treated as an image anchor (cleared, then the picture `AddPictureFromBytes`'d there at `logoScale`), never substituted as text — `imageExtension` sniffs PNG/JPEG/GIF/BMP/SVG from the bytes (`http.DetectContentType`), and `db/xlsx_export.go` blank-imports `image/png|jpeg|gif` so `image.DecodeConfig` (which excelize calls to size the picture) actually knows those formats. - `db/payment.go` — `CreatePayment`/`VoidPayment`: settles AR/AP at the **document's own frozen exchange rate**, not the payment's; the difference against the payment's own rate posts as a realized FX gain/loss plug line, never a retroactive edit to the original invoice's entry. Lettrage (tagging settled lines with a `reconciliation_groups` code, which would feed FEC's `EcritureLet`/`DateLet`) is **not implemented** — those two FEC columns are always blank, a legal value for an unlettered line, not a missing-field error. `CreatePayment`'s overpay guard is re-verified inside its own transaction via `getDocumentAmountPaidTx` right before the insert — a concurrent payment against the same document can't be encoded as a unique index (the check is an aggregate `SUM` over every other payment's applications, not a single-row lookup), so this is the one concurrency re-check site that needed its own re-check shape rather than the index+re-check pattern used elsewhere
- `db/cash_sale.go` / `POST /api/cash-sales` (`api/cash_sale.go`) — the Cash Book screen's single atomic write. `CreateCashSale` resolves-or-creates the client, creates the invoice (state `paid` iff `amountReceived == total`, else `sent`), inserts its line items, derives the invoice number from `organizations.invoice_number_format`/`_counter` **inside the same transaction** (`generateDocumentNumber`, the Go port of `src/utils/invoice.ts`'s token replacement) rather than trusting a frontend-sent number, posts the sale's GL entry, and — when any upfront amount was received — records the payment, its application and the settlement entry, all in one transaction, because chaining the separate endpoints could otherwise strand an unbalanced AR entry. Every read happens before `Beginx()` (`db.SetMaxOpenConns(1)` means a `d.DB` read while a `*sqlx.Tx` is open deadlocks, not errors — the same shape `UpdateInvoiceState`/`CreatePayment` use). It rejects a currency other than the organization's own (this screen never supports FX) and a sale with no line items. The settlement account resolves `defaultCashRegisterAccountId` → `defaultCashAccountId` → 409, and the invoice's `dueDate` is its own `date`, not `organizations.due_days` — a counter sale has no invoicing due-date concept
- `db/cash_sale_payment.go` / `POST /api/cash-sales/{id}/payments` (`api/cash_sale.go`, migration `0090`) — the Cash Book's **line-level** loan settlement. `CreateCashSalePayment` records a cash payment into `defaultCashRegisterAccountId` whose single `payment_applications` row names the invoice line it settles (`invoiceLineItemId`, nullable, `ON DELETE SET NULL`); the amount must not exceed that line's outstanding balance, checked before and re-checked inside the transaction against a fresh read (the F48 concurrency shape). It posts the Dr register / Cr AR entry and, when the payment clears the invoice's whole balance, flips `sent` → `paid` in the same transaction (both states need the same GL presence, so no posting changes) — the one place an invoice state is derived from payments, scoped to this purpose-built flow. Foreign-currency invoices are refused (no FX on this screen). A line's outstanding comes from the same `allocateInvoiceLines` the loan report uses (`db/dashboard.go`): each line's **amount** is the invoice total weighted by net line value (last line takes the rounding remainder), its **paid** is its own line-targeted applications plus a share of the invoice-level ones (an upfront cash-sale deposit, anything from the invoice page's payment panel) spread by line amount via `allocateCapped` — water-filling that never pushes a line past what it still owes after its own payments, so paying one line leaves every other line's balance exactly where it was. The GL is unaffected by line targeting: AR is still settled per invoice
- `db/cash_movement.go` / `POST /api/cash-movements` (`api/cash_movement.go`, migration `0080`) — records money *leaving* a cash register: a deposit to a bank account or an ad-hoc, document-less petty-cash expense, neither of which the `payments` table can represent (`payment_applications.documentType` is CHECK-constrained to `invoice`/`incoming_invoice`, and `payments`' own CHECK requires a client/vendor partner). `CreateCashMovement` follows `CreateCashSale`'s exact shape — all reads before `Beginx()`, then one transaction inserting the `cash_movements` row and posting its two-line Dr counter / Cr register entry via `postAutoEntryTx`. `counterAccountType` (`"bank"`|`"expense"`) is cross-checked against the counter account's own `accounts.type`, `accountId` defaults to `organizations.defaultCashRegisterAccountId` (409 if unset), and the returned `Balance` is `GetAccountBalance` for the register — deliberately no hard floor, so an over-withdrawal is displayed, not refused (the same "visibility, not a guarantee" stance as `GetInventoryValuation`). `cash_movements` is listed in `ResetOrganizationData`'s `transactionalDataTables` (`db/reset.go`) after the account/journal tables, and both its account columns are in `accountReferencingOrganizationColumns` (`db/account.go`)
- **Invoice number = loan number on the Cash Book.** `CashMovementDetail.InvoiceNumber`, `LoanStatusRow.InvoiceNumber` and `Payment.InvoiceNumbers` (a `db:"-"` field `GetPayments` fills with a second query over `payment_applications`, since one payment can settle several invoices; empty on every other read path) all carry it, and the three Cash Book exports (`db/report_export.go`) print it as an "Invoice" column — daily movements after Type, loan status after Date, payment history after Customer (joined with ", ")
- `db/cash_movement_details.go` / `GET /api/organizations/{orgId}/reports/cash-movement-details` (`api/cash_reports.go`) — `GetCashMovementDetails` is `GetDailyCashMovements`' per-transaction drill-down: inbound invoice payments (the "in" side) merged and date-sorted with `cash_movements` withdrawals (the "out" side, always kind `"withdrawal"`). Each inbound payment's `Kind` (`"sale"`/`"loan"`/`"repayment"`) is derived from its **position in the invoice's payment history** (`ROW_NUMBER() OVER (PARTITION BY documentId ...)`), not the invoice's current state — state is retroactive and would mislabel a three-month-old loan's repayment as today's "sale". Unlike `GetDailyCashMovements` it doesn't bucket by UTC day (a transaction list has no day-boundary ambiguity to resolve, only the caller's own range), and voided payments are excluded, so it can undercount a day that had a since-voided payment relative to the aggregate panel above it — deliberately not reconciled further
- `db/document_number.go` / `GET|PUT /api/organizations/{orgId}/document-number-settings/{documentType}` (`api/document_number_settings.go`, migration `0082`) — per-organization, per-document-type number format + **persisted counter** for the five types that previously used a hardcoded-prefix `Next*Number` scan: `order`, `purchase_order`, `delivery`, `inbound_delivery`, `production_order` (`documentNumberDefaults`, whose defaults reproduce the old `ORD-{number:3}`/`PO-{number:4}`/… output byte-for-byte). Invoices are deliberately **not** in this table — their numbering stays on the `organizations.invoice_number_format`/`_counter` columns. `GetDocumentNumberSetting` returns the type's default with counter 0 and `HasOverride:false` when no row exists ("absence means default", like `resolveTemplateBytes`); `UpdateDocumentNumberSetting` upserts and takes `counter` as a pointer so a format-only save doesn't reset it. `validateDocumentNumberFormat` accepts `{number}`, `{number:N}` (N 1–2 digits, so a hostile format can't allocate an unbounded string), `{year}`/`{y}`/`{month}`/`{m}`/`{day}`, and `{clientCode}`. `GenerateNextDocumentNumberTx` advances the counter once per document **inside the document's own insert transaction** (the same shape `CreateInvoice` already used), so a deleted document's number is never reissued; `PreviewNextDocumentNumber` is its read-only counterpart for each type's existing `next-number` prefill endpoint and does not consume the counter. `document_number_settings` is in `ResetOrganizationData`'s `masterDataTables` (`db/reset.go`)
- `journal_entries(fiscalYearId)` has an index (migration `0060`) — `CloseFiscalYear`'s activity snapshot, both GL exports below, and `db/gl_reports.go`'s report group-bys all filter by it, previously a full scan of an append-mostly, never-compacted table
- `db/gl_reports.go` — trial balance, P&L, balance sheet, AR/AP aging, all **computed on read** from `journal_lines`, the same "compute, don't cache" philosophy as `products.stockQuantity`. `BalanceSheet.CurrentEarnings` (revenue − expense over the cumulative window) is folded into `TotalEquity` so the sheet balances — nothing closes to retained earnings until a fiscal year is actually closed. AR/AP aging reuses `db/dashboard.go`'s existing outstanding-invoice query rather than a separate implementation, but computes the outstanding *amount* from `total − non-voided payment_applications`, not the document's raw total. F116 (multi-currency reporting, first slice): `OutstandingInvoice`/`OutstandingBill` also carry `Currency`/`ForeignTotal` — the same remaining balance in the document's own currency, unconverted, alongside the existing `Total` (always functional-currency, `× COALESCE(exchangeRate, 1)`) that every bucket sum is still expressed in. This is a display-only addition — the aging buckets themselves stay functional-currency, since summing balances from different currencies into one bucket wouldn't mean anything — not the broader by-currency P&L/balance-sheet breakdown or GL-export foreign columns the parent issue also raised and left unscoped. `GetInventoryValuation` (Phase 7, stretch sub-phase 7f) compares `organizations.defaultInventoryAccountId`'s posted GL balance against the independently-computed `Σ(stockQuantity × unitCost)` across every stock-enabled product (the same expression `db/dashboard.go`'s `getStockValuation` widget uses, without its top-10 truncation) — a visibility report, not a reconciliation guarantee: a nonzero `Difference` isn't automatically a bug (e.g. a product costed before the organization had `defaultInventoryAccountId` configured), it's a starting point for investigation
- `db/sales_reports.go` / `GET /api/organizations/{orgId}/reporting/{name}` (`api/reporting.go`) — the Reporting menu's document-derived sales/purchasing analytics: `GetRevenueByMonth`/`GetSalesByClient`/`GetSalesByProduct` (range + optional-limit versions of what used to be dashboard-only queries — `db/dashboard.go`'s `GetDashboardData` now calls these same functions with a rolling window and `limit=topN`, one source of truth instead of two copies), `GetPurchasesByVendor` (the purchasing-side mirror, `committedStates` = approved/paid), and `GetTaxSummary` (output VAT from `invoiceLineItems` vs input VAT from `incoming_invoice_line_items`, grouped by tax rate). Deliberately a different tier from `db/gl_reports.go` below — computed from source documents, not `journal_lines`, so a "revenue" number here isn't expected to reconcile with the GL's without the explanation in the file's top comment. `GetTaxSummary` also deliberately diverges from `db/gl_posting.go`'s tax-line building: a 0%-rate group is **not** skipped (zero-rated/exempt turnover is still reportable, unlike a GL line which can't be zero), and an unrated line item (`taxRate IS NULL`) rolls into its own `""` bucket instead of vanishing. An invoice's discount (`discountAmount`, migration `0088`) is taken off each group's base in proportion to its share of the subtotal (`invoiceNetFactor`, the same allocation as the GL and the VAT recap — it was ignored until audit F141, overstating output VAT). Tax is rounded once per tax-rate group **per document** (an inner per-`(documentId, taxRateId)` subquery) before summing across documents — matching `db/invoice_totals.go`'s `validateInvoiceTotals` rounding order, since summing raw amounts and rounding once at the end can be off by a cent even in a single currency with no FX involved
- `db/export_fec.go` / `GET /api/organizations/{orgId}/gl-export/fec` — France FEC statutory export (org admin **or accounting**): every posted/reversed journal line for a fiscal year as a tab-separated `SirenFECAAAAMMJJ.txt`. Every free-text source field is sanitized (tabs/newlines replaced with spaces) before joining, since one would otherwise silently shift every later column without raising an error. `ValidDate` is each entry's own `postedAt`, not `fiscal_years.lockDate` (a coarser year-level audit-prep lock, always NULL until something sets it — no UI does yet)
- `db/export_datev.go` / `GET /api/organizations/{orgId}/gl-export/datev` — Germany DATEV Buchungsstapel EXTF export (org admin **or accounting**), Windows-1252, semicolon-separated, CRLF. Its column layout, header structure, and field-encoding rules are cross-verified against two independently maintained open-source implementations (`ledermann/datev`, a Ruby gem, and `ameax/datev-extf`, a PHP library) plus a real `EXTF_Buchungsstapel.csv` example file — format category 21 ("Buchungsstapel") / format version 13, still **unvalidated against a live DATEV import**. DATEV's Buchungsstapel is a Konto/Gegenkonto (account/counter-account) format — one row per elementary two-sided posting, not one row per `journal_lines` row like FEC — so every auto-posted entry's single "anchor" line (AR/AP/bank/retained-earnings) becomes the implicit Gegenkonto for every other line; a manual entry with more than one line on *both* sides has no such anchor and either splits against `organizations.datevClearingAccountId` (if configured) or is collected as a blocking validation problem. Requires `organizations.datev_consultant_number` (1001–9999999), `datev_client_number` (1–99999), and a `datevAccountNumber` on every account referenced by a posted entry, all the same length (DATEV's single-value-per-batch Sachkontenlänge, 4–8 digits) — every missing/invalid field is collected into one `*db.ValidationError` rather than failing on the first, same idiom as `db/einvoice.go`. Belegdatum (column 10) is DDMM only (no year) — a different format from every other date field in this exporter, which is why it isn't `formatDATEVDate`. Encoding an out-of-cp1252 rune (free text is multi-locale here) replaces it with `encoding.ReplaceUnsupported` rather than failing the whole export. Deliberately unset: "Generalumkehr" (column 118) — a reversed entry and its reversal both export as ordinary opposite-side bookings, arithmetically correct but not specially flagged as a reversal for the importer
- `db/fiscal_year_closing.go` / `POST /api/fiscal-years/{id}/close` — `CloseFiscalYear` (org admin **or accounting**, **irreversible — there is no reopen endpoint**): posts one closing entry zeroing every revenue/expense account active in the year into `organizations.retainedEarningsAccountId`, closes every still-open `fiscal_periods` row under it, then marks the year `closed`. Must post the closing entry **before** flipping the year's own status — `resolveFiscalPeriodForDate` only resolves an open year. Unrealized FX revaluation (also originally scoped here) is **not implemented**: it needs a period-end market exchange rate, and this system has no rate oracle or period-end-rate input anywhere — every `exchangeRate` column (`db/exchange_rate.go`) is a one-time, manually-entered, frozen rate — so the computation has no input to work from, not just a missing implementation. the revenue/expense activity snapshot runs against `tx`, not `d.DB` — read outside the transaction, a posting committed in the gap between the pre-tx `GetFiscalYear` read and the transaction acquiring the connection would silently miss the closing entry. The final `UPDATE fiscal_years SET status = 'closed' ...` carries `WHERE status = 'open'` with a `RowsAffected` check, so two concurrent closes leave exactly one closing entry instead of each posting its own

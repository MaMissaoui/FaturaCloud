# cmd/seed-demo — Claude notes

Loaded only when working under `cmd/seed-demo/`. See also `README.md` here.

- `cmd/seed-demo/` (2026-09-09) — a standalone Go tool (the repo's first `cmd/`) that populates a demo organization with months of realistic, daily business activity (invoices, orders/deliveries, purchase orders/receipts/bills, payments) by driving the real REST API — a logged-in session, the CSRF header, real GL posting — rather than calling `db.Database` directly, so a run doubles as an API-layer smoke test. Every request body is built from the real `db.CreateXRequest` structs (imported, not hand-written `map[string]interface{}` literals) specifically because several of those structs mix JSON key conventions field-by-field (e.g. `CreateClientRequest.HouseNumber` serializes as `house_number` on an otherwise-camelCase struct) — see `cmd/seed-demo/README.md`'s "why HTTP, and why `db` types" note. `scheduler.go`'s day-keyed task queue is the mechanism every multi-step chain (an invoice's eventual payment; PO → receive → bill → pay) uses to say "come back and do this later"; `stock.go` keeps a local on-hand estimate so a delivery is never asked to ship more than purchasing has actually received. Deliberately never closes a fiscal year (irreversible — see `db/fiscal_year_closing.go` below) and deliberately keeps the "never gets paid" share of invoices/bills small (~3-5%) since it compounds across an 18-month run into an unrealistically large AR/AP aging tail otherwise — both tuned after actually running it end to end and looking at the Dashboard, not just checking the run exited 0. `imports.go` (F114) creates a consolidated shipment roughly monthly and links a handful of newly placed component purchase orders to it for the following ~3 weeks (`maybeLinkToImport`) so a receipt against one of them exercises `applyLandedCost`'s freight/customs spread and the Imports list has linked POs/committed value to show. `production.go` (2026-09-12, updated 2026-09-14 for BOM/read-back, updated again once Production Orders shipped in this same session) is what actually makes the "finished" motorcycle catalog sellable rather than just priced-and-catalogued. `setupBillsOfMaterials` defines a real BOM for every finished product once at startup (`PUT /api/products/{id}/bom`, a curated subset of one displacement class's components — not all 55, since getting every one simultaneously in stock via purchasing.go's uniform-random restocking turned out to be an unreliable coupon-collector problem) and `assembleBatch` reads each chosen product's real BOM back (`GET /api/products/{id}/bom`) before every batch to compute how many units are buildable — so a seeded organization's Products page shows real, populated recipes, not just this tool's private assumption. Consumption itself now drives the real Production Order feature (`db/production_order.go`): `assembleBatch` creates a draft order (`POST /api/production-orders`, which snapshots the same BOM server-side) then marks it `completed` (`PATCH .../status`), the same two-call flow the frontend's Create/"Mark as completed" buttons use, kept supplied by its own dedicated weekly procurement pass independent of ordinary purchasing. Completion enforces a real stock-availability check the old raw-movement simulation never had; a 409 there (the local on-hand estimate having drifted from server truth) skips that batch rather than failing the run, leaving a harmless order stuck in `draft` behind. Before this, `sales.go`'s stock-fulfilment path could never ship a "finished" good (nothing ever gave one on-hand stock), so `buildDeliveryCOGSGLLines` never fired and every seeded organization's Profit & Loss showed real revenue but permanently empty expenses; `db.GetProfitAndLoss` on a from-scratch run now shows a populated COGS line, confirmed against a real server. `catalog.go`'s `countryLocale`/`localeFor` resolve client/vendor company names, person names, cities, phone numbers, and VATIN format from the same `--country` flag `masterdata.go`'s `orgProfiles` uses for the organization's own address/chart-of-accounts profile, so e.g. `--country Tunisia` seeds Tunisian-looking clients and vendors, not German placeholder data with a Tunisian organization bolted on top. See the README for the full flag reference and what's still explicitly out of scope (serialized products, multi-currency). **Cash register account note** (the note `README.md` and `masterdata.go`'s `setupCashRegisterAccount` refer to): `organizations.defaultCashRegisterAccountId` is deliberately separate from `defaultCashAccountId` — every shipped chart-of-accounts template wires `defaultCashAccountId` to Bank, not the physical till, so a Cash Book sale or register report has nothing to resolve against until an admin picks the till account manually in Organization settings. Nothing wires it automatically for a real organization; this tool automates exactly that one manual step for the retail scenario (`masterdata.go`'s `setupCashRegisterAccount`, gated on `s.scenario.hasCashBookSales`): it resolves the generic chart's `1010` ("Cash") leaf account and sets `defaultCashRegisterAccountId` to it, so the scenario's `POST /api/cash-sales`/`POST /api/cash-movements` land in a register the Cash Book balance widget and Daily Cash Movements report actually watch

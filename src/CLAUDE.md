# src/ — Claude notes

Loaded only when working under `src/`. Project-wide invariants are summarized in the root `CLAUDE.md`; server-side rules for the data behind these pages are in `db/CLAUDE.md`.

## State Management

Uses Jotai atoms pattern with:

- Storage atoms for persistence (localeAtom, siderAtom)
- Database-connected atoms for entities (clientsAtom, invoicesAtom, etc.)
- Setter atoms for database operations (setClientsAtom, etc.)
- Each domain has its own file under `src/atoms/`

**Important**: never use Jotai module-level atoms for local UI state inside Modal or Drawer forms — the mask gets orphaned and freezes the UI. Use `useState` for all local drawer/modal state. `src/routes/settings/users.tsx` was the one page still violating this — its drawer's `open`/`editingId` state are now `useState`, matching every other Modal/Drawer form. The page's `searchAtom` stays module-level (list-page filter state persisting across navigation, the same pattern the other list pages use — a smell, not the freeze risk)

## Sidebar Navigation

Apart from two top-level items — **Dashboard** and **Cash Book** (`/cash-book`), in that order, before the groups — the sidebar is grouped into collapsible submenus (click the group to expand/collapse, same behavior for all groups — the active group auto-expands based on the current route via `defaultOpenKeys` in `src/layouts/base.tsx`):

- **Sales**: Invoices → Outbound Deliveries → Orders
- **Purchasing**: Imports → Purchase Orders → Goods Receipts → Incoming Invoices
- **Inventory**: Inventory → Production Orders
- **Master Data**: Clients → Vendors → Products → Bill of Materials → Organizations
- **Accounting**: Chart of Accounts → Journals → Fiscal Periods → Journal Entries → Trial Balance → Profit & Loss → Balance Sheet → AR Aging → AP Aging → Inventory Valuation → Daily Cash Movements (no standalone Payments page — recording/voiding a payment happens from the invoice/incoming-invoice detail page's `PaymentPanel`)
- **Reporting**: Revenue Trend → Sales by Client → Sales by Product → Purchases by Vendor → Tax Summary — document-derived sales/purchasing analytics (see `db/sales_reports.go`), a deliberately separate group from Accounting's GL-derived reports above

Settings is **not** a sidebar group (issue #183, 2026-09-10) — it moved to a gear icon in the header's top-right icon cluster (next to the theme toggle), opening an antd `Dropdown` with the same items the sidebar group used to have: Invoice, Tax rates, Payment terms, Units of measure, Document Templates, Document Numbering, Backup (platform admin only), Users (platform admin only), Countries (platform admin only), GL Export (org admin or accounting) — same conditional visibility, unchanged. The icon tints `colorPrimary` while any `/settings/*` route is active, replacing the sidebar's old selected-item highlight for that section. Moved to shrink the sidebar's total scroll height by one full group; the routes themselves (`/settings/*`) and their pages didn't change.

The repeatable component/quantity row UI itself (`src/components/products/bom-fields.tsx`) is shared with `src/components/products/form.tsx`'s own "Bill of Materials" card (still there, edited alongside the rest of the product while already in that record, with an "Open in Bill of Materials screen" link over to the dedicated drawer) — one implementation, two entry points into the same `PUT` endpoint, latest-wins on either save path, the same convention as `organizations.logo`/document template overrides. `bom-fields.tsx`'s row `Row` sets `wrap={false}` and its Select column `minWidth: 0` — a long component label (name + SKU, worse once translated) has an intrinsic content width wider than the row, and a flex column's default min-width is its content size, not 0; without both, the row silently wrapped and orphaned the delete button onto its own line below the qty input instead of letting the Select truncate with an ellipsis (a real bug caught live, not a hypothetical). Version history (`bill_of_materials_versions`/`bill_of_materials_version_lines`, migration `0074`): every `ReplaceBillOfMaterials` call snapshots the resulting new state as a new version — version 1 is the first recipe ever saved, not "state before the first edit" — unless the save is a no-op (same component set/quantities and `batchSize` as the latest version, compared against that version's own denormalized lines, not the live `bill_of_materials` table, since the two can legitimately diverge after a component is deleted — `ON DELETE CASCADE` on the live row vs. `ON DELETE SET NULL` on the historical one). A failed load of either the recipe or a past version is surfaced, not swallowed: the drawer shows an error with a Retry and **disables Save** while it stands — an empty form is indistinguishable from "no components yet", so saving from one would replace a real recipe with nothing. `bom-editor-drawer.tsx` shows "Current" plus a chip per past version (`GET .../bom/versions`); selecting one loads it read-only (`GET .../bom/versions/{id}`) with a "Restore this version?" `Popconfirm` in the footer instead of Save, calling `POST .../bom/versions/{id}/restore` — itself just a `ReplaceBillOfMaterials` call using that version's lines, so it creates a new version rather than rewriting history (**unconditionally**, even when the restored content equals the current recipe, which an ordinary save skips as a no-op — restore used to silently record nothing in that case), and 409s naming the component if any of the version's components was since deleted. The drawer's "Batch size" field is a pure entry-helper: quantities on screen are always "for a batch of N units", scaled by whatever `batchSize` the latest version was saved at (reloaded on open, not reset to 1) and rescaled in place if the user changes N mid-edit so each row's underlying per-unit meaning doesn't silently drift; divided back down before the API call. `db/product_bom.go`'s `roundBOMQuantity` (stored values) and the frontend's matching display-side rounding both use 4 decimal places. That is **not** enough to make the scale-divide-scale round trip exact, and the code doesn't claim it is: 1 unit entered at a batch of 3 stores `0.3333` and redisplays as `0.9999`, not `1` — an inherent consequence of storing 4 decimal places, asserted as correct by `db/product_bom_test.go`'s `TestBillOfMaterialsBatchSizeRoundTrip`. What the shared 4-decimal rounding _does_ guarantee is that the gap doesn't **compound**: re-saving that redisplayed `0.9999` divides back through the identical rounding, settles on `0.3333` again, and is correctly detected as a no-op for version history rather than drifting further on every open-then-save cycle. The downstream consequence is worth knowing: a 3-unit production run against that recipe consumes `0.9999` of the component, not `1`

There is deliberately **no** `GET /units-of-measure/{id}` endpoint — `unitOfMeasureAtom`'s read half looks the record up from the already-loaded list, since the list is always small; its write half follows the rethrow-after-toast convention so a failed save keeps the drawer open. The list this page maintains is what `src/components/products/form.tsx`'s "Base unit of measure" `Select` reads, and its default row is what prefills a new product — so a unit renamed or deleted here is felt on the Products form immediately, which is why `UpdateUnitOfMeasure` propagates a rename onto every linked `products.unit` in the same transaction
- `src/components/payments/payment-panel.tsx` — payment recording/void UI embedded in invoice/incoming-invoice detail pages; amounts passed in must already be cents (`unitsToCents`), not the raw invoice/bill `total`
- `src/components/mass-data/mass-data-excel-actions.tsx` — the Download/Upload Excel pair rendered next to the "New ..." button on every master-data list page (Clients, Vendors, Products, Tax Rates, Payment Terms, Units of Measure, Chart of Accounts) — one shared component, `resource` prop selects the table (see `db/mass_data.go` for the backend engine). Upload uses `Upload`'s `beforeUpload` returning `false`, the same take-over-the-request pattern `document-templates.tsx`'s upload already uses; a result with any failed row opens a `Modal` listing row/record/error, otherwise just a success toast. `onImported` is the page's own list-refetch atom setter (`setClientsAtom`, etc.) — passed in rather than owned by this component since each page's atom is different

## State Management

Uses Jotai atoms pattern with:

- Storage atoms for persistence (localeAtom, siderAtom)
- Database-connected atoms for entities (clientsAtom, invoicesAtom, etc.)
- Setter atoms for database operations (setClientsAtom, etc.)
- Each domain has its own file under `src/atoms/`

**Important**: never use Jotai module-level atoms for local UI state inside Modal or Drawer forms — the mask gets orphaned and freezes the UI. Use `useState` for all local drawer/modal state. `src/routes/settings/users.tsx` was the one page still violating this — its drawer's `open`/`editingId` state are now `useState`, matching every other Modal/Drawer form. The page's `searchAtom` stays module-level (list-page filter state persisting across navigation, the same pattern the other list pages use — a smell, not the freeze risk)

## Data loading

`oxlint`'s `react(set-state-in-effect)` rule is enforced at zero warnings (`--deny-warnings`), so a page never loads data by calling `setState` synchronously inside a `useEffect`. The patterns that replaced it (#428–#431):

- **List pages** load their atom with `useLoadOnPath(path, load, deps)` (`src/hooks/useLoadOnPath.ts`): it runs `load` on every visit to `path` (and when a primitive in `deps` changes) and returns the `loading` flag, derived from which location/deps the last settled load belongs to.
- **Reports, per-record counts and drawer lookups** use `useFetch(key, fetcher, empty)` (`src/hooks/useFetch.ts`): `key` is a list of primitives (ids, `.valueOf()` timestamps) and `null` means nothing to load, which returns `empty` and forgets any earlier result so the next record never shows the previous one's data. It returns `{data, loading, failed, reload}`; `reload` is the Retry/refresh button. A response for a superseded key is dropped, so no `requestIdRef` guard is needed. `empty` must be a stable value (a module constant for arrays/objects).
- **State that belongs to the record on screen** (a dirty flag, a status override, a picker, a load state) resets _during render_ when the value it depends on changes — keep the previous value in state and compare (`const [shownFor, setShownFor] = useState(x); if (shownFor !== x) { setShownFor(x); reset(); }`) — not in an effect. Form operations (`form.setFieldsValue`) stay in effects; they aren't React state.
- An effect that must set state does it only inside promise callbacks (`.then/.catch/.finally`), never in an `async` function whose `catch` could run synchronously.

## Number fields

Every number field is `NumberInput` (`src/components/number-input.tsx`), never antd's `InputNumber` directly, and never a plain `Input` read with `parseFloat`. It is `InputNumber` with `decimalSeparator` taken from `DecimalSeparatorContext`, which `src/app.tsx` provides from the active organization through `inputDecimalSeparator` (`src/utils/currencies.tsx`). That uses the same rule as `formatOrgCents`: the organization's country convention, else the UI language. So a Tunisian, French or German organization types "12,5" where its amounts read "12,50"; "." (`undefined`) leaves English inputs exactly as antd has them. Without it, antd's default parser _strips_ a comma, so "12,5" was stored as 125, and a plain `Input` + `parseFloat` read "19,5" as 19 (the tax-rate Percentage field, fixed with this). With "," set, a typed "." still parses, so a numpad that types "." keeps working. A field with its own `parser` bypasses `decimalSeparator`: use `suffix`/`prefix` for a unit sign instead of a `formatter`/`parser` pair. The context is read rather than `organizationAtom` because these fields live inside Modals and Drawers (see State Management); app.tsx reads the organization through `unwrap(..., prev => prev)` so the separator doesn't flip while a refresh is in flight.

The drawer's "Batch size" field is a pure entry-helper: quantities on screen are always "for a batch of N units", scaled by whatever `batchSize` the latest version was saved at (reloaded on open, not reset to 1) and rescaled in place if the user changes N mid-edit so each row's underlying per-unit meaning doesn't silently drift; divided back down before the API call. `db/product_bom.go`'s `roundBOMQuantity` (stored values) and the frontend's matching display-side rounding both use 4 decimal places. That is **not** enough to make the scale-divide-scale round trip exact, and the code doesn't claim it is: 1 unit entered at a batch of 3 stores `0.3333` and redisplays as `0.9999`, not `1` — an inherent consequence of storing 4 decimal places, asserted as correct by `db/product_bom_test.go`'s `TestBillOfMaterialsBatchSizeRoundTrip`. What the shared 4-decimal rounding _does_ guarantee is that the gap doesn't **compound**: re-saving that redisplayed `0.9999` divides back through the identical rounding, settles on `0.3333` again, and is correctly detected as a no-op for version history rather than drifting further on every open-then-save cycle. The downstream consequence is worth knowing: a 3-unit production run against that recipe consumes `0.9999` of the component, not `1`
